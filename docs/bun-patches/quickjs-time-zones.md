## QuickJS time zones

Class **Host feature**. QuickJS-ng 0.16.2 (bundled by rquickjs-sys 0.13.0) computes local time
in `getTimezoneOffset` (`third_party/rquickjs-sys/quickjs/quickjs.c`) with `localtime_r`, and
wasi-libc's knows only UTC, so `Date` ignored `process.env.TZ` on QuickJS. Now local time
follows `TZ` as on JSC ([`process.env` and `TZ`](process-env-semantics.md)): `getHours`,
`getTimezoneOffset`, `toString`, `toTimeString`, `toLocaleString` and the fallback `Intl`.
QuickJS reads the offset on every call, so a `Date` made before a write follows the new zone.

### Zone data

The zones come from data the runtime already ships: the FormatJS `Intl` fallback's
`add-all-tz` payload (`@formatjs/intl-datetimeformat` 7.8.2: every IANA zone with its
transitions from the earliest record through 2099) and its link table.
`scripts/vendor-intl.ts` now writes them to their own module,
`crates/bunwasm-runtime/src/js/tz_data.js` (1.36 MB raw), and `intl.js` reads that module
instead of carrying them inline, so the guest carries no second copy. Regenerating from the
pinned lockfile gives the same `intl.js` bytes plus the split.

`TZ` never loads that module. `crates/bunwasm-runtime/src/time_zone.rs` (original) finds the
one zone a name stands for in the embedded text (the `timeZoneEntries` and `timeZoneOffsets`
natives): the name's own entries when the data has them, else FormatJS's link.
`crates/bunwasm-runtime/src/js/time_zone.ts` (original) resolves the name to the zone Bun
reports after `process.env.TZ = name`:

- exact case (Bun keeps the previous zone for `asia/tokyo`);
- FormatJS's links (`US/Pacific` is `America/Los_Angeles`, `Asia/Calcutta` is `Asia/Kolkata`);
- every UTC name as `UTC`: `GMT`, `Etc/Unknown`, `Factory`, and the links to Etc/UTC and
  Etc/GMT, which have no entries (`Zulu`, `UCT`, `Universal`, `GMT0`, `Greenwich` and their
  `Etc/` forms);
- `EST5EDT`, `CST6CDT`, `MST7MDT` and `PST8PDT` as their cities (tzdata 2024b links, which
  FormatJS's data predates);
- `zone_ids.js` for the 19 names whose zone Bun reports differently (`America/Nipigon` is
  `America/Toronto`), so the zones FormatJS links elsewhere keep their own name and history
  (`Asia/Kuala_Lumpur`, `Europe/Jersey`, `Indian/Reunion`, `Pacific/Majuro`);
- Africa/Abidjan, which the data lacks, and the links to it that have no entries of their own
  (`Iceland` is `Atlantic/Reykjavik` with its entries; `Africa/Abidjan` is GMT all along).
  FormatJS's rule names in its link table (`1918`, `-5:00`) are not zones.

It turns the zone's entries into `[offset, time, offset, ...]` (seconds) and calls the
`setLocalTimeOffsets` native, and keeps the times its daylight flag changes for the zone's name.
An unknown name changes nothing and answers null, and an empty name restores UTC. A zone change
takes 0.5 to 2.2 ms on QuickJS, so a process that starts with `TZ` set starts as fast as one
without (208 ms either way under the native launcher). The fallback `Intl` takes the same zone
as its default, kept as named (FormatJS would report `Asia/Singapore` for
`Asia/Kuala_Lumpur`); a sweep of every zone Bun can report shows FormatJS formats each at
ICU's local time. Checked against ICU (native Bun) every three days at four times a day from
1950 to 2060: no offset differs for New York, London, Lord Howe, Kolkata, `Etc/GMT+3`, the UTC
names or `EST5EDT`.

### Engine

- `quickjs.c` (patch): `JS_bunwasm_SetLocalTimeOffsets` copies the table into fixed storage
  (1024 transitions; the largest zone, Europe/Guernsey, has 365), and `getTimezoneOffset`
  answers from it with a binary search while one is set. Building a date from local fields
  (`set_date_fields`) uses `getLocalTimezoneOffset`: of the offsets a day before and a day
  after, the first that maps back to the same local time, so a time in a spring-forward gap
  moves past it and a repeated fall-back time is its first occurrence, as JavaScriptCore does.
  Without a table, the libc's path runs unchanged.
- `Engine::set_local_time_offsets` (default false; QuickJS's `vm.rs` calls the hook) and the
  `setLocalTimeOffsets` native in `value_natives.rs` carry the table from JavaScript.
- `bootstrap.js` (QuickJS only): `toString` and `toTimeString` append the zone's name, as
  JavaScriptCore does ("GMT-0500 (Eastern Standard Time)", "(Coordinated Universal Time)" for
  UTC). JavaScriptCore asks ICU for the zone's standard or daylight name, so Almaty in 2000
  prints "Kazakhstan Time", not Intl's "Almaty Standard Time" for that date. The names come from
  `crates/bunwasm-runtime/src/js/zone_names.js`, generated by `scripts/generate-zone-names.ts`
  from native Bun 1.4.4's own `toString` (ICU 78.3), sampled monthly from 1970 to 2037 for the
  444 zones Bun can report. Each is keyed by FormatJS's offset and daylight flag, with the day
  each name starts (27.5 KB raw, 6.8 KB gzip). An offset the table never saw takes the zone's
  latest name for its daylight flag; a name ICU prints as the bare offset ("GMT-03:00") is built
  at run time. Printing a date never loads `Intl`.
- `bootstrap.js` (QuickJS's `toLocaleString`; JSC's and QuickJS's `toLocaleDateString` and
  `toLocaleTimeString`): with no arguments they print Bun's en-US text, "1/15/2024, 7:00:00
  AM", from the local fields without loading `Intl`; the fallback's default locale is en, as
  Bun's is. Other calls format through the fallback `Intl` with ECMA-402's defaults and keep one
  formatter per kind and locale, dropped when `TZ` changes. Their text has a space before AM/PM,
  as Bun's does, where FormatJS writes U+202F. QuickJS's own `toLocaleString` ignores its
  arguments and pads ("01/15/2024, 07:00:00 AM").

### Size

Against main at ee45ea714 the QuickJS guest grows by 50.9 KB raw and 14.6 KB gzip (gzip -9):
`bun.wasm` 21,589,569 to 21,635,778 bytes (gzip 6,792,006 to 6,804,659) and `quickjs.wasm`
1,460,842 to 1,465,493 bytes (gzip 476,123 to 478,066). Most of it is the zone names.

### Differences from native Bun 1.4.4

- The Browser engine keeps its host's zone: a page cannot change it (host limit).
- The zone data is FormatJS's, not ICU 78.3's; FormatJS does not record its tzdata release.
  Sampled weekly from 2024 to 2060, eight zones differ from ICU: Vancouver, Edmonton, Winnipeg,
  Inuvik, Yellowknife and Rainy_River from 2026-11-01 (FormatJS keeps UTC-7, -6 and -5 all
  year), and Casablanca and El_Aaiun from 2026-09-20. Review also found Cambridge_Bay, and Gaza
  and Hebron after 2040. FormatJS 7.9.0 has the same differences plus Havana from 2026-11-01,
  and 8.x (8.0.0 to 8.2.0) differs from ICU in 140 zones from 2024 on, so no newer release
  fixes them.
- `toString`'s zone names, checked against native Bun's `toString` every five days at noon UTC
  for all 444 zones: 1 wrong in 1,232,544 from
  2000 to 2037 (Asunción on 2024-10-11), none from 1970 to 1999, 1.2% from 1940 to 1969, 5.1%
  from 1900 to 1939 and 0.6% from 2038 to 2060. The misses outside the table's years come from
  FormatJS's offsets and daylight flags differing from ICU's, not from the names. The previous
  table (January and July of 2024 and 2026 only) had 163,859 wrong from 2000 to 2037.
- Africa/Abidjan's group without entries of its own is GMT all along; ICU keeps their local mean
  times before 1912 and Dakar's UTC-1 until 1941.
- After 2099 a zone keeps its last offset (the data's last transition is in 2099); ICU goes on
  applying the daylight saving rules.
- Offsets are whole minutes, as QuickJS's `getTimezoneOffset` returns them, so a local mean time
  before the zones (New York before 1883 is UTC-4:56:02) loses its seconds.
- Native Bun's argument-less `toLocaleString()` keeps the zone it first formatted in; bun-wasm's
  follows `TZ`, as its `toLocaleString("en-US")` and `Intl` do in Bun.
- The fallback `Intl` itself (FormatJS, on QuickJS and JSC) puts U+202F before AM/PM in
  `Intl.DateTimeFormat` output where Bun prints a space; the Date locale methods print the space.
  FormatJS also canonicalizes an explicit `timeZone` option through its links
  (`{ timeZone: "Asia/Kuala_Lumpur" }` reports and names Singapore); only the default zone keeps
  its name.

### Tests

`process-env-tz-zones` (QuickJS and JSC) compares zone by zone with native Bun 1.4.4 run in UTC:
New York, London, Lord Howe's 30-minute shift and its transition instants, Kolkata, `Etc/GMT+3`,
GMT, Etc/UTC, EST5EDT, `US/Pacific`, `Asia/Calcutta`, Berlin, Chatham, Casablanca,
`Etc/Unknown`, `Factory`, case. It also covers the UTC names `Zulu`, `GMT0` and
`Etc/Greenwich` after Tokyo; `Africa/Dakar`, `Iceland` and `Africa/Abidjan`; the merged zones
`Asia/Kuala_Lumpur`, `Europe/Jersey`, `Indian/Reunion`, `Pacific/Majuro` and `America/Nipigon`;
Coyhaique, Almaty and Qostanay; the rule name `1918`; past names (Mexico City 2020, Tehran 2020,
Moscow 2010 and 2012, São Paulo 2018, Istanbul 2015, Almaty 2000, London 1975); a gap and an
overlap in New York, unknown zones, an empty value, delete, argument-less locale strings at
midnight and noon, `Date()` and the locale methods' lengths. Locale strings are compared as
printed, with no U+202F normalization. `process-env-tz` (worker rules and Intl) runs on QuickJS
too. The Rust lookup's unit tests in `time_zone.rs` run against the embedded data.
