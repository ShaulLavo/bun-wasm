# JSC Proxy gets forwarded without native recursion

`Source/JavaScriptCore/runtime/ProxyObject.cpp` in `jsc/webkit-wasi.patch`, from Bun's WebKit fork at `3d3257150c40a1aabdc5f8b48d5b33d0413674cb`. Class **Port**.

## The problem

A Proxy with no `get` trap forwards a property read to its target. When the target is another Proxy, JSC recursively enters `performProxyGet` and the property-slot lookup. Each level consumes host Wasm stack as well as the 512 shadow-stack bytes reserved by the WASI port. On small browser and Node worker stacks, the host can run out before the soft guard throws a catchable `RangeError`.

## The change

`performDefaultProxyGet` and `callProxyGetTrap` contain the existing default lookup and trap-call code. Both helpers compile on every platform. Non-WASI builds retain the original recursive algorithm and call these helpers.

On WASI, `performProxyGet` walks a local `current` pointer through Proxy targets. Every pass reads that Proxy's target and handler, checks revocation, and resolves `get` through that Proxy's own trap cache. A trap receives its level's target, the key and the original receiver. The existing validation checks the result against that target. A handler exception or invariant failure returns immediately.

A non-Proxy target uses `PropertySlot(receiver, Get)`, `getPropertySlot` and `slot.getValue`, so a final-target accessor still sees the original receiver. Private names return `undefined` before the walk. No other Proxy internal method changes.

The function's existing entry reservation and soft guard remain. Each forward to another Proxy runs `WASM_RESERVE_STACK(512)` before `vm.isSafeToRecurseSoft()`. The reservation has function lifetime and accumulates on the shadow stack. The function epilogue restores it on success and on every guest exception return. The guard still throws the existing stack-overflow `RangeError`. No budget, reserve, parser setting or host deadline changes.

The loop allocates no heap continuation records. Target links keep each current Proxy reachable from the caller-rooted chain. `Strong<JSObject>` handles root the captured target, handler and fresh trap across native handler lookup, argument conversion and the trap call, including when the handler getter revokes their Proxy. The fixture revokes Proxies during handler lookup and keeps a fresh trap alive across an explicit collection to exercise that lifetime requirement.

For native-only lifetime acceptance, WASI builds provide an opt-in `BUN_WASM_JSC_PROXY_GET_GC=1` collection control, restricted to the fixture's `bunWasmNativeLifetime` property. It collects immediately after `getHandlerTrap` returns to the forwarding loop, and again in `callProxyGetTrap` after target, key and receiver conversion but before the native call. Each forced collection writes one `bun-wasm Proxy get lifetime collection` record to stderr, so the final-product logs prove that the control executed. With the variable absent, it performs no collection and preserves the forwarding algorithm. The dedicated `tests/jsc-embedding/proxy-get-lifetime` fixture revokes its Proxy inside the handler getter, returns a fresh trap, and leaves the maker's JavaScript frame before the read. The trap observes the revoked handler through `this`, as well as the captured target, converted key and receiver. This makes the handler and fresh trap native-only captures at both collection points.

## Tests

`tests/fixtures/proxy-get-forwarding` runs on QuickJS, JSC and the browser engine with output generated by native Bun. It covers chains of 1, 2 and 50 Proxies, explicit receivers, a trap in the middle, handler lookup order, a Proxy handler, self and deeper revocation, trap-level invariants, symbol and index keys, callable targets, handler and default-lookup exceptions, and trap mutation. The JSC gates require a 200000-level chain to throw a catchable `RangeError`, followed by a successful read. A browser host that completes the same chain must return the correct value.

The blocking JSC embedding control runs the fixture with a 320 KiB Node worker stack and the existing 800 KiB diagnostic guest budget. The unmodified engine traps at that tuple. The same finalized JSC product runs the native-only lifetime fixture with the targeted collection control enabled. Acceptance covers the split `dist/bun-jsc.wasm` and `dist/jsc-engine.wasm` pair and the shared-group `target/shared-native/program-jsc/bun.wasm` and `jsc-engine.wasm` pair. Each finalized pair must emit both collection markers and the fixture's single `ok` line. `scripts/jsc-embedding.test.ts` checks both collection placements and that the WASI loop charges each forward before its guard and does not recursively call `performProxyGet`. The original `stack-getter-headroom` fixture and its 1 MiB worker, 800 KiB guest, must-catch assertion remain unchanged.
