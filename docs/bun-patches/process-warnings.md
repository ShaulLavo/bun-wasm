Bun registers a native `onWarning` listener when it creates `process`, unless `NODE_NO_WARNINGS` is exactly `"1"` or `--no-warnings` was given, and builds the printer on the first warning. `bootstrap.js` loads `process_warning` right after it defines the `process` global, and loading it runs `install`, so `listenerCount("warning")` is 1 at startup and `removeAllListeners("warning")` silences the print. The printer is Bun's: `(node:PID) [CODE] Name: message`, the `detail` line, the one-time `--trace-warnings` hint, `--disable-warning` names and codes filtering only the print, `--redirect-warnings` or `NODE_REDIRECT_WARNINGS` appending to a file, and `.stack` read only while `process.traceProcessWarnings` (or `traceDeprecation` for deprecations) is set.

`emitWarning` follows Bun's argument handling: an options object supplies `type`, `code`, `detail` and `ctor`, a function argument is the constructor, `type` and `code` must be strings, and the warning must be a string or an `Error`. `code` and `detail` are non-enumerable. A deprecation is dropped under `process.noDeprecation`, thrown on a later tick under `process.throwDeprecation`, and every other warning is emitted as `'warning'` on the next tick. Where Bun's native code creates the error inside `emitWarning` and lets JavaScriptCore format the stack lazily, the port names the error and then calls `Error.captureStackTrace(error, ctor || process.emitWarning)`, as Node does, so engines that fix the stack header at capture time still print the warning type.

`--no-deprecation`, `--throw-deprecation`, `--trace-deprecation`, `--trace-warnings`, `--pending-deprecation` and `--no-warnings` define `noDeprecation`, `throwDeprecation`, `traceDeprecation`, `traceProcessWarnings`, `pendingDeprecation` and `noProcessWarnings` as read-only, enumerable, configurable `true` properties, Node's `addReadOnlyProcessAlias`. Bun reads these flags once for the whole process; here a worker guest's launch carries only its conditions, so `worker_threads.ts` passes the worker's parsed warning flags to `configure` before its preloads run. That replaces the earlier `internal.workerNoWarnings` early return, which also hid warnings from user listeners. `--disable-warning` and `--redirect-warnings` are read only in their `=` form, because the CLI keeps unknown flags as single arguments.

`process.ts` keeps its own `noDeprecation: false` property, so an unflagged `process.noDeprecation` stays an ordinary writable property, as in [process no-deprecation](process-no-deprecation.md).

`tests/fixtures/process-warnings` compares every case above with native Bun 1.4.4 output, through child `bun -e` runs, on QuickJS, JavaScriptCore and the browser engine (`checks/native-process-warnings.json`).
