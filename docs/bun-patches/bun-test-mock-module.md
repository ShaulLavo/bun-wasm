`mock.module(specifier, factory)` resolves the specifier from the calling file (the first non-runtime stack frame) the way an import would, ignoring earlier mocks, so a package is mocked at its `import` entry as in Bun. The resolver maps that target to a plugin module key: a file by its path, a missing relative or absolute file by its path normalized against the caller's directory, a builtin by its canonical `node:` name, and any other missing name by the name itself. Every later import or `require()` that resolves to the target, through any spelling, loads the key, whose exports are the factory's result; mocking the same target again replaces the earlier mock. A builtin mock covers imports only: `require("node:os")` keeps the real module, as native Bun 1.4.4 does. `require.resolve`, `import.meta.resolve(Sync)` and `Bun.resolveSync` report the target, not the key. `Bun.plugin.clearAll()` removes every mock.

The factory runs once, on first use, and a non-object result is Bun's `mock(module, fn) requires a function that returns an object`. As in Bun, `import()` waits for a thenable result, so an async factory's resolved value is what the import sees, while `require()` takes the result as it is until it settles (a sync factory's thenable is just a value there). Every dynamic-import path (`import_requests.ts` for QuickJS and JSC, and for the browser engine `web/src/engine-host.js` with native modules or `esm_loader.ts` with registration records) asks `bun_test.js` to settle a pending mock before loading it, and the settled value replaces the cached one. A missing file is also found through its absolute `file:` URL. A factory that loads its own target gets an empty object instead of recursing; native Bun then also returns that empty module to the outer import, which bun-wasm does not copy.

Native Bun also rewrites the exports of a module that was already imported. bun-wasm cannot patch an evaluated ES module namespace on every engine, so a module imported before `mock.module` keeps its original exports; call `mock.module` first, or import the module dynamically afterwards, as Bun's documentation shows.

`cargo test -p bunwasm-runtime resolve` covers re-mocking, missing files, builtins and package entries in the resolver. `tests/fixtures/bun-probe-test` (`probe.test.ts` and `module-mocks.test.ts`) compares re-mocking through another spelling, `require.resolve`, caller-relative missing files, builtin spellings, a dual package and the argument errors with native Bun on every engine.
